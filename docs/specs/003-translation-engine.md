# 003: 翻訳エンジン(チャンク分割・応答検証・リトライ)

## 目的

`002-settings-and-llm-adapter.md` で確立したアダプター境界の内側で、LLM への実際の翻訳リクエストを構成するロジック(チャンク分割・応答パース・検証・リトライ)を実装する。本仕様は単体テストで完結できる範囲(純粋なドメインロジック)を対象とし、MOD / クエスト / Patchouli / カスタムファイルそれぞれの入出力仕様は後続の機能仕様で扱う。

参照: `../feature-spec.md` §5.2(チャンク分割)、§5.3(応答検証・リトライ)、§5.5(差分更新ロジック)。

## 対象範囲

### チャンク分割(feature-spec.md §5.2)

- **エントリ数ベース**(既定): `Map<String, String>` のエントリを設定チャンクサイズで固定長分割する。
- **トークンベース**(オプトイン): プロバイダー別の概算トークン数がしきい値を超えないよう貪欲法で分割する。単一エントリがしきい値を超える場合は文末(`.` `!` `?`)で分割を試み、失敗時はそのまま送信する。
- チャンク粒度の非対称性を意図的に維持する(feature-spec.md §16.1): 本仕様ではチャンク分割関数自体を汎用実装とし、「キー単位」(MOD 向け)と「ファイル/本単位(常に1チャンク)」(クエスト・ガイドブック向け)の両方の呼び出しパターンをサポートできるインターフェースにする。実際にどちらを使うかは各機能仕様側で選択する。

### 応答検証・リトライ(feature-spec.md §5.3)

- LLM 応答のパース: `key: value` 形式の行を正規表現で抽出する。
- 全キーが復元できない場合、Markdown 装飾やヘッダー行を除去した上で行位置ベースの対応付けにフォールバックする。
- 元のキー数と翻訳後のキー数が一致しない場合はエラーとして扱う。
- チャンク単位で既定 3 回(設定可能)リトライする。
- API キー不正・認証エラー(401 / Unauthorized 相当)はリトライせず即座に失敗させる。
- 429 / `retry-after` ヘッダーによるレート制限検出時は、指定された待機時間の後にリトライする。
- 全リトライ失敗時は当該チャンクをスキップし、他のチャンクの処理を継続する(部分成功を許容)。

### 差分更新ロジック(feature-spec.md §5.5)

- 対象言語ファイルが存在する場合、その内容を読み込む(存在しない場合は通常の全件翻訳と同じ扱い)。
- 翻訳元のキー集合から、対象言語ファイルに既に存在するキーを除外し、不足分のキーのみを翻訳ジョブの入力とする。
- 翻訳完了後、既存の対象言語ファイルの内容と新たに翻訳した不足キーをマージして書き出す。既存キーの値は上書きしない。
- 不足キーが1件もない場合は翻訳ジョブ自体を作成せず「スキップ」として扱う。
- このロジックは MOD・Better Quests(標準/直接)・FTB Quests(KubeJS lang)・Patchouli ガイドブックの、キー単位で構造化されたフォーマットに共通利用できる形で実装する(SNBT 直接編集は対象外、feature-spec.md §4.2)。

## 対象外

- HTTP クライアントの実装・実際のネットワーク呼び出し(`002` のアダプター骨組みを利用するが、通信先の仕様確認・実測は対象外)。
- MOD / クエスト / Patchouli / カスタムファイルそれぞれの抽出・出力フォーマット(`004`〜`007` で扱う)。
- 進捗表示・キャンセル(`008-progress-log-history.md` で扱う)。
- プロンプトテンプレートへのプレースホルダー置換 UI(`002` で扱い済み。本仕様では置換処理そのもの(`{language}` `{line_count}` `{content}` の文字列置換)を実装する)。

## 受け入れ条件

1. エントリ数ベースのチャンク分割関数に対し、チャンクサイズより多いエントリを渡すと、指定サイズで固定長分割されることを単体テストで検証する(端数チャンクも正しく生成される)。
2. トークンベースのチャンク分割関数に対し、概算トークン数がしきい値を超えないように分割されることを単体テストで検証する。単一エントリがしきい値を超える場合は文末記号での分割を試み、分割できない場合はそのまま1エントリとして返すことを検証する。
3. 見積り失敗時にエントリ数ベースへフォールバックする設定(既定 ON)が、トークン見積り関数が例外を投げるケースで正しく機能することを検証する。
4. `key: value` 形式の応答を渡すと、正規表現ベースのパーサーが正しいキー→値のマップを復元することを検証する。
5. Markdown 装飾(コードブロック記号、見出し記号等)やヘッダー行が混入した応答に対し、行位置ベースのフォールバックが機能し、元のキー数と一致する場合は正しく対応付けられることを検証する。
6. 元のキー数と翻訳後のキー数が一致しない応答を渡すと、エラーとして扱われる(例外またはエラー結果を返す)ことを検証する。
7. リトライロジックが、一時的な失敗(タイムアウト・5xx 相当)に対して設定回数までリトライし、成功すれば結果を返すことを検証する。
8. 401 / Unauthorized 相当のエラーに対しては、リトライせず即座に失敗することを検証する。
9. 429 相当のレート制限エラーに対し、`retry-after` 相当の値を尊重して待機してからリトライすることを検証する(テストでは実待機を避け、待機時間の計算ロジックのみを検証する)。
10. 全リトライ失敗後、当該チャンクはスキップ扱いとなり、他のチャンクの処理が継続されることを、複数チャンクを含むバッチ処理のテストで検証する。
11. 差分更新ロジックに対し、(a) 対象言語ファイルが存在しない場合は全キーが翻訳対象になる、(b) 一部キーが既存の場合は不足キーのみが翻訳対象になる、(c) 全キーが既存の場合はジョブを作成せずスキップ扱いになる、の3パターンを単体テストで検証する。
12. 差分更新のマージ処理で、既存キーの値が新たな翻訳結果によって上書きされないことを検証する(ユーザーによる手動修正の保護)。
13. プロンプトテンプレートの `{language}` `{line_count}` `{content}` プレースホルダーが正しく置換され、置換対象外の文字列(例えば本文中にたまたま含まれる `{` `}`)を誤って置換しないことを検証する。
14. `flutter analyze` / `flutter test` が成功する。

## 移行上の判断

- 元のキー数と翻訳後のキー数の不一致をエラーとする挙動は、旧 `docs/spec.md` §7.2.0 の設計意図をそのまま踏襲する(feature-spec.md §5.3)。
- 差分更新は旧実装では未実装(設計意図のみ)だった機能を新規に実装するものであり、既存翻訳スキップの言語コード依存ハードコードリストは廃止し、キー比較ベースの汎用ロジックに統一する(feature-spec.md §16.2)。
