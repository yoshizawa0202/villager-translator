# 006: Patchouli ガイドブック翻訳機能

## 目的

`.jar` 内の Patchouli ガイドブックを検出し、翻訳結果を JAR に追記する機能を実装する。Patchouli 本体の翻訳データ解決仕様は下記「Patchouli 出力構造の検証結果」で確定済み(ディレクトリミラー方式)であり、これに従って実装する。

参照: `../feature-spec.md` §8(Patchouli ガイドブック翻訳機能)、§16.2(出力構造の対応方針)、§16.4(実装後に実機確認が必要な項目)。

## Patchouli 出力構造の検証結果

旧実装は `en_us/` 配下の複数ファイルにまたがる抽出結果を `patchouli_books/{bookId}/{language}.json` という単一のフラットファイルにまとめて出力していた。これが Patchouli 本体の実際のロード仕様と一致するかを、公式ドキュメントとソースコードで検証した。

- **公式ドキュメント**(Patchouli Getting Started: https://vazkiimods.github.io/Patchouli/docs/patchouli-basics/getting-started/ )に以下の記載がある(該当箇所の要約):
  - `en_us` フォルダの内容が常に「メイン」として読み込まれる。
  - 翻訳者は自分の言語コードのフォルダ(例 `zh_cn`)を `en_us` と同じ階層に作成し、上書きしたい任意のファイルをそこに配置する。ゲーム言語が変更されると自動的に読み込まれる。
  - 翻訳者は、上書きしないファイルを自分のフォルダに含めてはならない。
  - Entry JSON の ID はファイルパスから決まる(例 `en_us/entries/misc/cool_stuff.json` → `patchouli:misc/cool_stuff`)。翻訳側もこの相対パスを維持したファイルとして提供する必要がある。
- **ソースコード**(`VazkiiMods/Patchouli` リポジトリ、`Xplat/src/main/java/vazkii/patchouli/client/book/BookContentResourceDirectLoader.java` ほか)でも、リソース探索パスは `patchouli_books/{bookId}/{locale}/{folder}/...` という、`en_us` と同一のディレクトリ階層を `locale` ごとに走査する形で構築されている。ファイル群を単一ファイルへ集約するロジックは見当たらない。

**結論**: 出力構造は「`en_us/` と同じディレクトリ構造を `assets/{modId}/patchouli_books/{bookId}/{lang}/` 配下にミラーする」方式を採用する。旧実装の単一フラットファイル(`{lang}.json`)方式は Patchouli の仕様と一致しないため採用しない。

**実装後に実機確認が必要な残課題**(受け入れ条件 11 参照): 上記調査で「ファイル単位・ディレクトリミラーで上書きする」ことは確認できたが、以下は文書上の確証が得られなかったため、安全側の設計で実装した上で、実機(実際の Minecraft + Patchouli 環境)での動作確認を必須とする。
  - 翻訳先ファイルが `name`/`description`/`title`/`text` など翻訳対象キーのみを含む部分的な JSON(スパース上書き)でも Patchouli が正しく解決するか、それとも `icon`/`category`/`pages` 配列の型情報など en_us 側と同一の構造を持つ完全な JSON である必要があるか。Gson デシリアライズ(`BookEntry`/`BookCategory` 等の POJO)を用いる実装であり、フィールド単位のマージ処理は見当たらないため、**本仕様では安全側に倒し、en_us ファイルの完全なコピーに対象キーの翻訳値のみを適用した「フルコピー方式」を採用する**(下記「翻訳・出力」参照)。実機確認でスパース上書きも許容されると判明した場合でも、フルコピー方式は上位互換のため変更不要と想定される。
  - `book.json`(`data/{modId}/patchouli_books/{bookId}/book.json`)内の `name`/`landing_text` 等のローカライズキーは、今回のスキャン対象(`assets/.../en_us/**/*.json`)に含まれないため翻訳対象外とする。これにより本の表示名やランディングページの一部が翻訳言語に反映されない可能性がある。実機確認の上、必要であれば対象範囲(`006` の後続改修または `007`)を見直す。

## 対象範囲

### スキャン(feature-spec.md §8.1)

- MOD スキャン(`004`)と同じ `.jar` 一覧を使う。
- 各 JAR 内の `assets/{modId}/patchouli_books/{bookId}/en_us/**/*.json` に一致する全ファイルを、ページ・カテゴリのサブディレクトリを含めて再帰的に検出する。
- 各ファイルから `"name"` `"description"` `"title"` `"text"` キーの値のみを対象に抽出する(JSON 全体を構造的にパースせず、値抽出に限定する軽量な方式)。
- 同一本(`{modId}:{bookId}`)に属する全ファイルの抽出結果を1つの翻訳単位に統合する。
- 既存翻訳の判定は、`en_us/` 配下で検出した各ファイルに対応する `assets/{modId}/patchouli_books/{bookId}/{lang}/` 配下の同一相対パスのファイル有無・内容で行う(ディレクトリミラー方式、上記「Patchouli 出力構造の検証結果」参照)。本全体としては、「ファイルの相対パス + JSON 内のキー位置」を複合キーとしたエントリ集合(`Map<String, String>` 相当)に正規化した上で `003` の差分更新ロジックに渡し、本単位で不足しているエントリのみを翻訳対象とする。

### 翻訳・出力(feature-spec.md §8.2)

- 翻訳結果は JAR ファイルへ追記する形で書き込む: コピー→全エントリをストリーミング転送→新規エントリ追加→原本を置き換える、というアトミックな差し替え手順にする。
- 出力ファイルは `en_us/` と同じディレクトリ構造を `assets/{modId}/patchouli_books/{bookId}/{lang}/` 配下にミラーして書き込む(「Patchouli 出力構造の検証結果」参照)。各出力ファイルは、対応する en_us ファイルの完全なコピーを基に、抽出した `name`/`description`/`title`/`text` の値のみを翻訳結果で置き換えたものとする(フルコピー方式。`icon`/`category`/`pages` の型情報など、翻訳対象外のキーはそのまま維持する)。
- MOD 翻訳と異なり書き込み前の JAR バックアップが旧実装には存在しなかったが、`AGENTS.md` の「元データ保全」制約に従い、**JAR 書き換え前に原本を退避するバックアップを必須の受け入れ条件に含める**(旧実装からの意図的な改善)。

## 対象外

- MOD・クエスト・カスタムファイルのスキャン・翻訳(`004`、`005`、`007` で扱う)。
- 進捗表示・キャンセル・ログ・履歴の横断的な UI 統合(`008` で扱う)。
- Patchouli 以外のガイドブック MOD(該当する場合は将来検討)。

## 受け入れ条件

1. 出力構造がディレクトリミラー方式(`assets/{modId}/patchouli_books/{bookId}/{lang}/` 配下に `en_us/` と同じ相対パスでファイルを書き出す)で実装されていることを検証する(「Patchouli 出力構造の検証結果」参照)。
2. `assets/{modId}/patchouli_books/{bookId}/en_us/**/*.json` に一致する全ファイルが、ページ・カテゴリのサブディレクトリを含めて再帰的に検出されることを検証する。
3. 各ファイルから `"name"` `"description"` `"title"` `"text"` キーの値のみが抽出され、それ以外のキー(構造情報等)は翻訳対象に含まれないことを検証する。
4. 同一本(`{modId}:{bookId}`)に属する複数ファイルの抽出結果が1つの翻訳単位に統合されることを検証する。
5. 対象言語の `{lang}/` 配下のミラーファイル群が JAR 内に全て存在する本には「既存」判定が、一部または全部が存在しない本には「新規/差分更新対象」判定がテーブル表示用になされることを検証する。
6. 既存翻訳が存在する本に対して差分更新モードを適用すると、`003` の差分更新ロジックにより不足エントリ(ファイル相対パス+キー位置単位)のみが翻訳され、既存エントリの値が変更されないことを検証する。
7. 出力される各翻訳ファイルが、対応する en_us ファイルの構造(`icon`/`category`/`pages` 等の翻訳対象外キー)を変更せず、`name`/`description`/`title`/`text` の値のみが翻訳結果に置き換えられている(フルコピー方式)ことを検証する。
8. 翻訳結果が JAR に書き込まれる際、コピー→ストリーミング転送→新規エントリ追加→原本置き換えの手順で行われ、処理完了後に JAR 内の既存エントリ(翻訳対象以外のファイル)が破損・欠落しないことを検証する。
9. JAR への書き込みを開始する前に、対象 JAR の原本がセッションディレクトリ配下にバックアップされることを検証する。
10. 書き込み処理の途中で例外が発生した場合、原本の JAR が破損した状態で残らないこと(アトミックな差し替えが機能し、失敗時は元の JAR かバックアップから復元可能であること)を検証する。
11. **実装後の要実機確認**: 生成した `{lang}/` ミラーファイルを実際の Minecraft + Patchouli 環境に配置し、ガイドブックが対象言語で正しく表示されることを確認する。フルコピー方式で問題が生じた場合、または部分 JSON(スパース上書き)で十分と判明した場合は、本仕様の「Patchouli 出力構造の検証結果」を更新する。
12. `flutter analyze` / `flutter test` が成功する。

## 移行上の判断

- Patchouli 翻訳結果の出力ファイル構造は、公式ドキュメント(Patchouli Getting Started)とソースコード調査の結果、`en_us/` と同じディレクトリ構造を `{lang}/` 配下にミラーする「フルコピー方式」に決定した。旧実装の単一フラットファイル(`{lang}.json`)方式は Patchouli の仕様と一致しないため不採用とする。詳細は「Patchouli 出力構造の検証結果」を参照(feature-spec.md §8.2、§16.2 の指摘に対する回答)。スパース上書きの可否など細部は受け入れ条件 11 のとおり実装後に実機確認する。
- JAR 書き換え前のバックアップを新規に追加する。旧実装にはこのバックアップが存在しなかった(feature-spec.md §12、§16.2)。
