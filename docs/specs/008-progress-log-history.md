# 008: 進捗・キャンセル・ログ・バックアップ・履歴、および4タブ統合

## 目的

`004`〜`007` で個別に実装した MOD / クエスト / Patchouli / カスタムファイルの各翻訳機能を横断する、進捗表示・キャンセル・ログ・バックアップ・翻訳履歴の共通基盤を実装する。また、4タブ(MOD / クエスト / ガイドブック / カスタムファイル)を1つの画面に統合し、プロファイルディレクトリ選択の共有・タブ切替制御といった全体レイアウトを完成させる。個別機能が先行実装されているため、本仕様はそれらを並行して整理・統合する最終回として位置づける。

参照: `../feature-spec.md` §3(画面構成・共通 UI フロー)、§10(進捗表示・キャンセル)、§11(ログ機能)、§12(バックアップ機能)、§13(翻訳履歴機能)。

## 対象範囲

### 全体レイアウト・タブ統合(feature-spec.md §3.1)

- 単一画面、4タブ(MOD / クエスト / ガイドブック / カスタムファイル)を統合する。
- 翻訳中・スキャン中はタブ切替を禁止する(誤操作によるジョブ喪失防止)。
- ヘッダー: アップデート通知(feature-spec.md §14 により本サイクルでは対象外、UI 上のプレースホルダーのみ検討)、ログビューア起動、履歴ダイアログ起動、テーマ切替、設定(歯車)。

### 各タブ共通のツールバー・テーブル(feature-spec.md §3.2)

- 「プロファイルディレクトリを選択」の選択結果を全タブで共有する(MOD タブで選んだディレクトリはクエスト/ガイドブック/カスタムファイルタブにも引き継がれる)。
- 対象言語セレクタはタブごとに独立した選択状態を持つ。
- 完了ダイアログ: 成功/失敗/合計件数、結果一覧(検索可能)、ログ表示ボタン。

### 進捗表示・キャンセル(feature-spec.md §10)

- 二階層の進捗: 単一ファイル進捗(現在処理中のジョブ内、0〜100%)と全体進捗(バッチ内の完了件数/総件数)。
- テキスト表示形式: 「X / Y 件完了 (Z%)」。
- キャンセルは協調的: チャンクとチャンクの間でキャンセルフラグを確認し、現在処理中のチャンクの完了を待ってから停止する。実行中の LLM への HTTP リクエスト自体は中断しない。
- 保存粒度: キャンセル時点で完了しているチャンク(キー群)は出力ファイルに書き込み、未完了のキーは省略する(元の英語のままでは出力しない)。
- 未完了で終わった対象は、次回同じ対象を差分更新モードで再実行すれば不足キーが自動的に埋められる(キャンセル再開専用の機構は設けない)。
- 完了時にはシステム通知と完了サマリを表示する。

### ログ機能(feature-spec.md §11、Issue #10 による改訂)

- 処理ログはメモリ上のリングバッファ(直近 N 件)とリアルタイム表示を持つ。
- ログには日時・レベル(Debug/Info/Warning/Error)・処理種別・メッセージを含める。
- 翻訳中は詳細ログ、アイドル時は要約ログ(進捗の節目・エラーのみ)を表示する。
- ログの永続化先は2系統とする(Issue #10「翻訳失敗が多発するが実行ログが追えない」への対応)。
  - **プロファイルログ**(`{プロファイル}/logs/localizer/{sessionId}/session.log`):
    「開始」「対象ファイル(MOD/クエスト/ガイドブック/カスタムファイル)ごとの
    成功・失敗」「完了サマリ」「トップレベルの例外」など、大きな粒度のログの
    みを書き出す。1チャンク(1翻訳単位)ごとの詳細な実行内容は含めない。
  - **アプリケーションログ**(`{ApplicationSupportDirectory}/logs/localizer/
    {sessionId}/session.log`、プロファイルに依存しない): 上記に加えて、
    1チャンク(1翻訳単位)ごとの実行内容・結果(リトライ回数・成否・エラー
    概要)を含む全ログを書き出す。粒度の細かいデバッグログはここでのみ追える。
    アプリ内のヘッダーから専用ボタンで開き、履歴ダイアログと同じ UI で
    参照できる。
- チャンク(1翻訳単位)の処理結果は、成功(リトライなし)は Debug、リトライを
  伴う成功は Warning、リトライを使い切った失敗(スキップ)は Error として記録
  する。対象ファイル単位の成功/失敗はプロファイルログにも記録するため、
  Info(成功)/Warning(失敗)として扱う。

### バックアップ機能(feature-spec.md §12)

- `004`〜`006` で実装済みの各バックアップ(リソースパック、SNBT 原本、Patchouli JAR 原本)が、共通のセッションディレクトリ構造(`logs/localizer/{sessionId}/backup/...`)に統一されていることを確認・整理する。
- バックアップには保持期間・自動削除ポリシーを設けない(明示的な削除操作のみ)。

### 翻訳履歴機能(feature-spec.md §13)

- 実行ごとに `logs/localizer/{sessionId}/translation_summary.json` を書き出す(対象言語、各項目の種別・名前・成功/失敗・翻訳キー数/全キー数)。
- 履歴ダイアログでは、セッションディレクトリを指定して過去セッション一覧(日時降順)を表示し、行を展開すると当該セッションの詳細とログを閲覧できる。
- 履歴は現在アクティブなプロファイルディレクトリとは独立して、別ディレクトリを指定して閲覧できる。

## 対象外

- 自動アップデート機能(feature-spec.md §14、対象外)。
- 各機能固有のスキャン・翻訳ロジックの変更(`004`〜`007` で実装済みのものを前提とし、本仕様では横断的な統合のみを扱う)。
- 翻訳実行前の概算コスト表示(feature-spec.md §18、将来検討事項)。

## 受け入れ条件

1. 4タブが1画面に統合され、いずれかのタブでスキャンまたは翻訳が実行中の間は他タブへの切替が禁止されることを検証する(UI テストまたはウィジェットテスト)。
2. MOD タブでプロファイルディレクトリを選択すると、クエスト/ガイドブック/カスタムファイルタブにも同じディレクトリが反映されることを検証する。
3. 各タブの対象言語セレクタが互いに独立しており、あるタブでの選択が他タブに影響しないことを検証する。
4. 翻訳処理中、単一ファイル進捗(0〜100%)と全体進捗(完了件数/総件数)が独立して更新され、「X / Y 件完了 (Z%)」形式でテキスト表示されることを検証する。
5. キャンセル操作を行うと、現在処理中のチャンクの完了を待ってから処理が停止し、それ以降のチャンクは実行されないことを検証する。
6. キャンセル時点で完了していたチャンク分のキーが出力ファイルに書き込まれ、未完了のキーは元の英語のまま出力されず省略されることを検証する。
7. キャンセルにより一部キーが未翻訳のまま残った対象を、差分更新モードで再実行すると、不足していたキーのみが翻訳され埋められることを検証する。
8. 翻訳完了時にシステム通知と、成功/失敗/合計件数を含む完了サマリダイアログが表示されることを検証する。
9. 処理ログがリアルタイムに UI へ表示され、同時にプロファイル・アプリケーションそれぞれの `logs/localizer/{sessionId}/` 配下のログファイルへ日時・レベル・処理種別・メッセージを含む形式で永続化されることを検証する。
10. アイドル時は要約ログ(進捗の節目・エラーのみ)、翻訳中は詳細ログが表示されることを検証する。
10a. プロファイルログには「開始」「対象ファイルごとの成功/失敗」「完了サマリ」「トップレベルの例外」などの粗い粒度のログのみが書き出され、1チャンク単位の詳細ログは書き出されないことを検証する(Issue #10)。
10b. アプリケーションログ(プロファイル非依存)には、プロファイルログの内容に加えて1チャンク単位の詳細な実行内容・結果(成功/失敗・リトライ回数・エラー概要)が書き出されることを検証する(Issue #10)。
10c. アプリケーションログはヘッダーの専用ボタンから履歴ダイアログと同じ UI で参照できることを検証する(Issue #10)。
11. `004`〜`006` で実装済みの各バックアップ(リソースパック・SNBT 原本・Patchouli JAR 原本)が、いずれも同一セッションの `logs/localizer/{sessionId}/backup/` 配下に格納されることを検証する。
12. 翻訳実行のたびに `logs/localizer/{sessionId}/translation_summary.json` が生成され、対象言語・各項目の種別/名前/成功失敗/翻訳キー数・全キー数が記録されることを検証する。
13. 履歴ダイアログで過去セッション一覧が日時降順で表示され、行を展開すると当該セッションのログ・詳細が閲覧できることを検証する。
14. 履歴ダイアログで、現在アクティブなプロファイルディレクトリとは別のディレクトリを指定してセッション一覧を閲覧できることを検証する。
15. `flutter analyze` / `flutter test` が成功する。
16. Windows に影響する変更のため `flutter build windows --release` が成功する。

## 移行上の判断

- 進捗の保存粒度(部分成功時に未完了キーを省略して出力する)は旧実装の挙動を踏襲する。これは Minecraft のリソースパックが欠けたキーを MOD 本来の `en_us` にフォールバックする性質を前提とした設計であり、部分的な lang ファイルでも実害がないため維持する(feature-spec.md §10)。
- キャンセル再開の専用機構は設けず、差分更新の仕組みをそのまま流用する(feature-spec.md §10)。
