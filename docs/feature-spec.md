# 機能仕様書: MinecraftModsLocalizer からの機能移植

## 0. この文書の位置づけ

- この文書は `../MinecraftModsLocalizer`(以下「旧アプリ」)の実装とドキュメント(`../MinecraftModsLocalizer/docs/spec.md`)を突き合わせて調査した結果に基づく、Villager Translator の**機能一覧・移植方針の正本**です。
- `AGENTS.md` が定める仕様駆動開発では、実装前に `docs/specs/NNN-*.md` へ目的・対象外・受け入れ条件を書く必要があります。本文書はその前段として、移植対象の全体像を先に固定し、後続の `docs/specs/002-*.md` 以降を機能単位で切り出すための土台とします。**本文書単体は受け入れ条件の正本ではありません。** 各 `docs/specs/00N-*.md` を作成する際は、該当セクションを参照しつつ、その回のスコープに合わせて受け入れ条件を再定義してください。
- 旧アプリの実装には、ドキュメント(`docs/spec.md`)と実際のコードの間に乖離や既知の不整合がいくつか存在します。本文書ではそれらを「旧実装の挙動」として記録した上で、「移行時の判断」として Villager Translator でどう扱うかを明記します。単純な丸写しはしません(`AGENTS.md` の方針どおり)。

## 1. 全体像

### 1.1 目的

Minecraft の MOD 言語ファイル、クエスト(FTB Quests / Better Quests)、Patchouli ガイドブック、および任意の JSON/SNBT ファイルを、LLM(OpenAI / Anthropic / Google Gemini)を用いてローカル環境で一括翻訳する。

### 1.2 対象ユーザー

Minecraft MOD プレイヤー・モーダー。日本語 UI を主対象とする(旧アプリは英語/日本語切替、Villager Translator は日本語を既定言語とする)。

### 1.3 主要機能一覧

| # | 機能 | 概要 |
|---|---|---|
| 1 | 設定管理 | LLM プロバイダー・API キー・プロンプト・チャンクサイズ・対象言語の管理 |
| 2 | LLM 翻訳エンジン | アダプターパターンによるプロバイダー切替、チャンク分割、応答検証、リトライ |
| 3 | MOD 翻訳 | `.jar` 内の `lang` ファイルを検出し、リソースパックとして翻訳出力 |
| 4 | クエスト翻訳 | FTB Quests(SNBT / KubeJS lang)、Better Quests(JSON / .lang)を検出・翻訳 |
| 5 | Patchouli ガイドブック翻訳 | `.jar` 内の Patchouli 本を検出し、翻訳結果を JAR に追記 |
| 6 | カスタムファイル翻訳 | 任意ディレクトリ配下の JSON / SNBT を再帰的に翻訳 |
| 7 | 進捗表示・キャンセル | ファイル単位・全体単位の進捗、協調的キャンセル |
| 8 | ログ | 処理ログのリアルタイム表示・セッション単位のログファイル保存 |
| 9 | バックアップ | 翻訳前の原本保全(SNBT・リソースパック) |
| 10 | 翻訳履歴 | セッション単位の実行結果をディレクトリから閲覧 |
| 11 | 自動アップデート | GitHub Releases 経由の更新確認・適用 (対象外、§14 参照) |

### 1.4 想定ディレクトリ構成(Minecraft プロファイル)

旧アプリはインスタンス/プロファイルのルートディレクトリを選択させ、以下を前提にパスを解決する。Villager Translator でも同じ前提を踏襲する。

```
{プロファイルルート}/
├── mods/                          # MOD 翻訳・Patchouli 翻訳の対象
├── config/
│   ├── ftbquests/quests/          # FTB Quests (標準)
│   ├── ftbquests/normal/          # FTB Interactions Remastered
│   └── betterquesting/DefaultQuests.lang
├── kubejs/assets/kubejs/lang/     # FTB Quests (KubeJS 経由)
├── resources/betterquesting/lang/ # Better Quests (標準)
├── resourcepacks/{パック名}/       # MOD 翻訳の出力先
└── logs/localizer/{セッションID}/  # 実行ログ・バックアップ・履歴
```

## 2. 用語・データモデル

Dart への移植を想定したモデル定義方針(旧実装 `src/lib/types/minecraft.ts` 相当)。

- `TranslationTargetType`: `mod` | `quest` | `patchouli` | `custom`
- `TranslationTarget`: スキャン結果としてテーブルに表示される1行。`{ type, id, name, path, relativePath?, selected, questFormat?: ftb|better, langFormat?: json|lang, hasExistingTranslation? }`
- `ModInfo`: `{ id, name, version, jarPath, langFiles, patchouliBooks, langFormat }`
- `LangFile`: `{ language, path, content: Map<String, String> }`(常にフラットな key→value)
- `TranslationJob` / `TranslationChunk`: 翻訳の実行単位。チャンクは `pending -> processing -> completed|failed` の状態を持つ
- `TranslationResult`: 完了ダイアログ・履歴に表示する1件分の結果 `{ type, id, displayName?, targetLanguage, outputPath, success, sessionId? }`

## 3. 画面構成・共通 UI フロー

### 3.1 全体レイアウト

- 単一画面、4つのタブ: **MOD** / **クエスト** / **ガイドブック** / **カスタムファイル**。
- 翻訳中・スキャン中はタブ切替を禁止する(誤操作によるジョブ喪失防止)。
- ヘッダー: アップデート通知、ログビューア起動、履歴ダイアログ起動、テーマ切替、設定(歯車)。

### 3.2 各タブ共通のツールバー・テーブル

- 「プロファイルディレクトリを選択」ボタン: OS ネイティブのフォルダ選択ダイアログ。**選択結果は全タブで共有**する(MOD タブで選んだディレクトリはクエスト/ガイドブック/カスタムファイルタブにも引き継がれる)。
- 「スキャン」ボタン: ディレクトリ未選択時は無効。スキャン中は進捗(現在処理中のファイル名・件数)を表示。
- 「翻訳」ボタン: 対象未選択、または対象言語未選択の場合は無効。
- 対象言語セレクタ: タブごとに独立した選択状態を持つ(同一セッション内で MOD は日本語、クエストはフランス語、のような使い分けが可能)。
- テーブル: チェックボックス列(ヘッダーで全選択)、種別ごとの列、列ヘッダークリックでソート、名前/ID の部分一致検索。
- 「翻訳中」表示: 単一ファイル進捗バーと全体進捗バーの2段表示。
- 「キャンセル」ボタン: 協調的キャンセル(§10 参照)。
- 完了ダイアログ: 成功/失敗/合計件数、結果一覧(検索可能)、ログ表示ボタン。

### 3.3 対象言語管理ダイアログ

- 既定言語(削除不可): 日本語(ja_jp)、简体中文(zh_cn)、한국어(ko_kr)、Deutsch(de_de)、Français(fr_fr)、Español(es_es)、Italiano(it_it)、Português-Brasil(pt_br)、Русский(ru_ru)。
- カスタム言語の追加(表示名 + 言語 ID のペア)・削除が可能。

## 4. 設定機能

### 4.1 LLM 設定

- プロバイダー選択: OpenAI / Anthropic / Google Gemini。
- プロバイダーごとに個別の API キーを保存する(`apiKeys: { openai, anthropic, gemini }`)。
- モデル選択はコンボボックス方式とする。旧実装の完全自由入力(タイプミスや存在しないモデル名を入力できてしまう)を改め、プロバイダーごとに代表的なモデルを選択肢として提示しつつ、一覧にないモデルも使えるよう「カスタム」項目で自由入力にフォールバックできるハイブリッド方式にする。
    - OpenAI の選択肢例: `gpt-4o-mini`(既定)、`gpt-4o`、`gpt-4.1`、`gpt-4.1-mini`、`o4-mini`
    - Anthropic の選択肢例: `claude-3-5-haiku-20241022`(既定)、`claude-3-5-sonnet-20241022`、`claude-opus-4-1`
    - Google Gemini の選択肢例: `gemini-1.5-flash`(既定)、`gemini-1.5-pro`、`gemini-2.0-flash`
    - 上記の一覧は実装時点の代表例であり、各プロバイダーの新モデルリリースに合わせて更新する保守対象とする。一覧はコード上の定数として1箇所にまとめ、`docs/specs/002-*.md` 実装時に確定させる。
    - 「カスタム」選択時のみモデル名のテキスト入力欄を表示する。
- 詳細設定: 最大リトライ回数(既定 3)、temperature(既定 1.0、0.0〜2.0)。
- システムプロンプト / ユーザープロンプトを個別に編集可能。既定プロンプトは §5.4 参照。
- API キー入力欄は表示/非表示切替アイコンを持つ。
- 「デフォルトに戻す」ボタンで全設定を初期値へリセット。

**移行時の判断**: 旧実装ではプロバイダー識別子が設定値(`"google"`)とアダプター内部 ID(`"gemini"`)で不一致だった(`llm-adapter-factory.ts` は `"gemini"` で分岐するが設定 UI は `"google"` を保存)。Villager Translator では**識別子を `gemini` に統一**し、設定・アダプター・UI のどこでも同じ文字列を使う。

### 4.2 翻訳設定

- トークンベースのチャンク分割の ON/OFF。ON 時は「チャンクあたり最大トークン数」(既定 3000、1000〜10000)と「見積り失敗時にエントリ数ベースへフォールバックするか」(既定 ON)を設定可能。
- 「既存翻訳の扱い」設定(既定: 差分更新)。3つのモードから選択する:
    1. **スキップ**: 対象言語ファイルが既に存在する場合、その対象は翻訳しない(現状維持)。
    2. **差分更新**(既定): 対象言語ファイルが存在する場合、`en_us` 側に存在し対象言語ファイルには存在しないキーのみを翻訳して追記する。既存キーの値(ユーザーによる手動修正を含む)は変更しない。詳細ロジックは §5.5 参照。
    3. **全て再翻訳**: 既存の対象言語ファイルの有無に関わらず、常に全キーを翻訳し直して置き換える。
    - 適用対象は MOD の lang ファイル、Better Quests(標準/直接)、FTB Quests(KubeJS lang)、Patchouli ガイドブックの、いずれも**キー単位で構造化されたフォーマット**。SNBT 直接編集(§7.1)はファイル全体を書き換える形式でキー単位の差分検出ができないため対象外とし、常に全文を再翻訳する。
- リソースパック名(既定: `VillagerTranslator`)。
- カテゴリ別チャンクサイズ: MOD(既定 50)、クエスト(既定 1)、ガイドブック(既定 1)。範囲は 1〜1000。

**移行時の判断**: 旧実装は「既存翻訳スキップ」チェックを MOD タブで最大3回(スキャン時・翻訳前プレチェック・各対象の翻訳直前)冗長に実行していた。Villager Translator では**スキャン時の表示用チェックと、翻訳直前の実チェックの2箇所のみ**に整理する。

**移行時の判断(差分更新)**: 旧 `docs/spec.md` §7.2.1 は「`{language}.json` が既に存在する場合、未翻訳部分だけを翻訳する」という差分更新を設計意図として明記していたが、旧実装の実コードは「既存なら丸ごとスキップ」という二値判定しかサポートしておらず、この設計意図は実現されていなかった。Villager Translator では差分更新を正式に実装し、(a) MOD 更新で `en_us` に新規キーが追加されても追従できる、(b) ユーザーが対象言語ファイルを手動修正しても再実行で上書き消失しない、という2つの実用上の課題を解消する。

### 4.3 プロンプトテンプレート

- プレースホルダー: `{language}`(対象言語)、`{line_count}`(行数)、`{content}`(`key: value` 形式で1行1エントリに整形した本文)。
- 既定システムプロンプト・ユーザープロンプトの内容は旧アプリ `docs/spec.md` §7.2.0 の「Default Prompt」を踏襲し、Minecraft 固有の翻訳ルール(行数厳守、特殊記号 `%s` `$1` `\"` の保持、`§` カラーコードの保持、意訳優先)を含める。

**移行時の判断**: 旧実装には `{x}`(単一波括弧)と `{{x}}`(二重波括弧)の**2種類の既定プロンプト定義が併存**しており、実際に置換処理が対応しているのは単一波括弧のみだった(設定 UI のプレースホルダー表示と実処理が食い違うバグ)。Villager Translator では**単一波括弧 `{language}` `{line_count}` `{content}` に一本化**する。

## 5. LLM 翻訳エンジン

### 5.1 アダプターパターン

`AGENTS.md` の「翻訳 API は差し替え可能なアダプター境界の内側に閉じ込める」という制約に対応する中核機能。

- 共通インターフェース: `translate(content: Map<String,String>, targetLanguage, promptTemplate?) -> Map<String,String>`。
- 各プロバイダーアダプターは system/user 形式のチャットメッセージを構築し、temperature・リトライ・レート制限検出(429 / `retry-after` ヘッダー)を担う。
- `validateApiKey(key)`: 設定画面での疎通確認用(軽量な API 呼び出しで検証)。

### 5.2 チャンク分割

- **エントリ数ベース**(既定): `Map` のエントリを設定チャンクサイズで固定長分割。
- **トークンベース**(オプトイン): プロバイダー別の概算トークン数がしきい値を超えないよう貪欲法で分割。単一エントリがしきい値を超える場合は、文末(`.` `!` `?`)で分割を試み、失敗時はそのまま送信する。
- チャンク粒度は機能によって異なる(意図的な非対称性、§16.1 で明記):
  - MOD: **キー単位**でチャンク化(1チャンクに複数キー)。
  - クエスト・ガイドブック・カスタムファイル SNBT: **ファイル/本単位**でチャンク化(ファイル全体を1つの翻訳エントリとして送信)。

### 5.3 応答検証・リトライ

- LLM 応答のパース: `key: value` 形式の行を正規表現で抽出。全キーが復元できない場合は、Markdown 装飾やヘッダー行を除去した上で行位置ベースの対応付けにフォールバック。
- **元のキー数と翻訳後のキー数が一致しない場合はエラーとして扱う**(旧 `docs/spec.md` §7.2.0 の「If the list length differs...it is treated as an error」を踏襲)。
- リトライ: チャンク単位で既定 3 回(設定可能)。API キー不正・認証エラー(401 / Unauthorized 相当)は**リトライせず即座に失敗**させる。
- 全リトライ失敗時は当該チャンクをスキップし、他のチャンクの処理を継続する(部分成功を許容)。

### 5.4 既定プロンプト・既定言語

- 既定プロンプトは旧 `docs/spec.md` の内容を移植(§4.3 参照)。
- 既定言語一覧は §3.3 のとおり。

### 5.5 差分更新ロジック

「既存翻訳の扱い」(§4.2)が **差分更新** の対象は、次の手順で処理する。

1. 対象言語ファイルが存在する場合、その内容を読み込む(存在しない場合は通常の全件翻訳と同じ扱いになる)。
2. 翻訳元(`en_us` 等)のキー集合から、対象言語ファイルに**既に存在するキー**を除外し、不足分のキーのみを翻訳ジョブの入力とする。
3. 翻訳完了後、既存の対象言語ファイルの内容と、新たに翻訳した不足キーをマージして書き出す。**既存キーの値は上書きしない**(ユーザーの手動修正を保護する)。
4. 不足キーが1件もない場合は、翻訳ジョブ自体を作成せず「スキップ」として扱う。

この手順により、キャンセルや失敗で一部のキーが未翻訳のまま残った場合も、次回同じ対象を差分更新モードで再実行するだけで不足分を自動的に埋められる(§10 参照)。適用対象・対象外は §4.2 のとおり。

## 6. MOD 翻訳機能

### 6.1 スキャン

1. `{プロファイル}/mods/` 直下(非再帰)の `.jar` を列挙。
2. 各 `.jar` をアーカイブとして開き、MOD ID/名前/バージョンを次の優先順で取得: `fabric.mod.json` → `META-INF/mods.toml`(Forge/NeoForge)→ `META-INF/MANIFEST.MF`(最終手段、ID は `unknown`)。いずれも取得できない MOD はスキップしログに記録する。
3. `*/lang/en_us.json` または `*/lang/en_us.lang` を検出し、`lang` フォーマット(JSON/LANG)を記録する。**言語ファイルが存在しない MOD は対象一覧から除外**する。
4. `_comment` キーや BOM・制御文字を除去してから JSON/LANG をパースする(破損ファイルは MOD 単位でスキップし、スキャン全体は継続する)。
5. Patchouli 本の検出も同じパスで行う(§7 参照)。
6. 対象言語の `assets/{modId}/lang/{lang}.json|.lang` が JAR 内に既に存在するかを確認し、テーブルに「既存/新規」バッジを表示する(§4.2 の「既存翻訳の扱い」設定に関わらず、表示用の判定として常に行う)。

テーブル列: MOD 名、MOD ID、`mods/` からの相対パス、フォーマット(JSON/LANG)、既存翻訳バッジ。

### 6.2 翻訳

1. 選択対象をアルファベット順にソートし、決定論的な処理順にする。
2. 「既存翻訳の扱い」が**スキップ**の場合、翻訳直前に再確認し、既存であればスキップ件数としてカウントする。**差分更新**の場合は §5.5 の手順で不足キーのみを翻訳し、既存キーの値は変更しない。
3. 全対象がスキップされた場合(または差分更新で不足キーが1件もなかった場合)、リソースパックを作成せずに終了する。
4. `resourcepacks/{設定したパック名}/pack.mcmeta`(format 9)を作成し、翻訳結果を **1回の実行で選択した全 MOD を1つのリソースパックにまとめて**書き込む(MOD ごとに別パックは作らない)。
5. 出力: `{リソースパック}/assets/{modId}/lang/{targetLanguage}.json|.lang`(キーはソートして出力)。元の `.jar` ファイルは変更しない。
6. 翻訳完了後、生成したリソースパック全体をセッションディレクトリ配下にバックアップする。

## 7. クエスト翻訳機能(FTB Quests / Better Quests)

1タブで2つの独立したクエスト形式を扱う。

### 7.1 FTB Quests

- **KubeJS 経由**: `{プロファイル}/kubejs/assets/kubejs/lang/en_us.json` が存在する場合、そのディレクトリ内の `*.json` を対象とする(既に翻訳済みファイル名パターンは除外)。
- **出力先(設計判断)**: 旧 `docs/spec.md` §7.3.2/§7.9.2 は、KubeJS 経由の場合に翻訳結果を **`kubejs/assets/kubejs/lang/{targetLanguage}.json` と `kubejs/assets/ftbquests/lang/{targetLanguage}.json` の2箇所へ出力する**と明記していたが、旧実装の実コードは前者(`kubejs/lang/`)にしか書き込んでいなかった。これは旧実装側の不備(設計意図の未実装)と判断し、Villager Translator では**設計意図どおり両方のパスへ出力する**。誤ったパスにしか出力しないと**翻訳ファイルは生成されるがゲーム内表示に反映されない**という致命的な不具合になり得るため、片方のみへの出力は選択しない。ただし FTB Quests / KubeJS Localization が実際にどちらのパスから翻訳文字列を読み込むかは未検証のままであり、`docs/specs/005-quest-translation.md` の実装後に実機(FTB Quests + KubeJS 導入環境)での目視確認を別途行う。
- **SNBT 直接編集**: KubeJS lang が存在しない場合、`config/ftbquests/quests`(標準)→ `config/ftbquests/normal`(FTB Interactions Remastered 用)→ `config/ftbquests`(フォールバック)の順に存在するディレクトリを探し、配下の `*.snbt` を再帰的に列挙する。
- SNBT からの翻訳対象文字列抽出は、`title` `subtitle` `description` の値を正規表現で抽出する方式(旧 `docs/spec.md` §7.2.2 のサンプル実装を踏襲。エスケープされた `"` は前方のバックスラッシュ数で判定)。
- **SNBT ファイルは翻訳後、同じファイルに直接上書きする**(言語サフィックスを付けない)。Minecraft がそのまま読み込める状態を維持するため。
- 翻訳前に選択した SNBT ファイルをセッションディレクトリへバックアップする。

### 7.2 Better Quests

- 標準: `{プロファイル}/resources/betterquesting/lang/*.json`(非再帰)。
- 直接: `{プロファイル}/config/betterquesting/DefaultQuests.lang`(単一ファイル)。
- 出力: 標準形式は `{basename}.{targetLanguage}.json` を同ディレクトリに新規作成。直接形式は `DefaultQuests.{targetLanguage}.lang` を新規作成。原本は変更しない。
- `.lang` はキー=値形式のためソート済み `key=value` 行として再シリアライズする。

### 7.3 共通事項

- クエストは**ファイル全体を1つの翻訳単位**として LLM に渡す(キー単位分割はしない)。SNBT はテキスト全体を、JSON/LANG は変換した JSON 文字列全体を送信し、応答をそのまま構造に戻す。
- 既存翻訳の判定は、SNBT は「常に未翻訳扱い」(直接上書きのため判定不能、常に全文再翻訳)とし、JSON/LANG(KubeJS lang、Better Quests 標準/直接)は隣接する `{stem}.{lang}.json` の有無で判定する。JSON/LANG は §4.2 の「差分更新」対象であり、キー単位で不足分のみ翻訳できる。

**移行時の判断**: 旧実装には SNBT の内容種別(`json_keys` / `direct_text`)を判定する処理があったが、実際の出力ロジックでは使われていない未配線のコードだった。Villager Translator では**判定ロジック自体を持たず**、`title`/`subtitle`/`description` の正規表現抽出のみを実装する(§7.1 の方式で十分機能するため)。

## 8. Patchouli ガイドブック翻訳機能

### 8.1 スキャン

1. MOD スキャン(§6.1)と同じ `.jar` 一覧を使う。
2. 各 JAR 内の `assets/{modId}/patchouli_books/{bookId}/en_us/**/*.json` に一致する全ファイルを検出する(ページ・カテゴリのサブディレクトリを含めて再帰的に)。
3. 各ファイルから `"name"` `"description"` `"title"` `"text"` キーの値のみを対象に抽出する(JSON 全体を構造的にパースするのではなく、値抽出に限定する軽量な方式)。
4. 同一本(`{modId}:{bookId}`)に属する全ファイルの抽出結果を**1つの翻訳単位に統合**する。
5. 既存翻訳の判定は、`en_us/` 配下の各ファイルに対応する `assets/{modId}/patchouli_books/{bookId}/{lang}/` 配下(`en_us` と同一の相対パス)のファイル有無・内容で行う(ディレクトリミラー方式。詳細・根拠は `docs/specs/006-patchouli-translation.md` の「Patchouli 出力構造の検証結果」参照)。ファイル相対パス+キー位置を複合キーとしたエントリ集合に正規化した上で、§4.2 の「差分更新」対象に含める(不足エントリのみ翻訳して既存ファイルにマージする)。

### 8.2 翻訳・出力

- 翻訳結果は JAR ファイルへ追記する形で書き込む(コピー→全エントリをストリーミング転送→新規エントリ追加→原本を置き換え、というアトミックな差し替え手順)。
- **出力構造の決定**(旧実装からの引き継ぎ検討事項に対する回答): 旧実装は抽出元が `en_us/` 配下の複数ファイルにまたがっていても、出力は `patchouli_books/{bookId}/{language}.json` という**単一のフラットファイル**にまとめていた。公式ドキュメント(Patchouli Getting Started: https://vazkiimods.github.io/Patchouli/docs/patchouli-basics/getting-started/ )およびソースコード(`VazkiiMods/Patchouli` の `BookContentResourceDirectLoader.java` 等、`patchouli_books/{bookId}/{locale}/{folder}/...` という en_us と同一階層を locale ごとに探索する実装)の調査の結果、Patchouli は**`en_us/` と同じディレクトリ構造を `{lang}/` 配下にミラーする方式**を前提としており、単一フラットファイルへの集約は仕様と一致しないと判断した。各ミラーファイルは対応する en_us ファイルの完全なコピーに翻訳値のみを適用する「フルコピー方式」とする(スパース上書きが可能かは文書上未確証のため、実装後に実機確認する。§16.4 参照)。詳細は `docs/specs/006-patchouli-translation.md` を参照。
- MOD 翻訳と異なり、**書き込み前に JAR 自体のバックアップは行わない**(セッションログ・進捗記録のみ)。Villager Translator では `AGENTS.md` の「元データ保全」制約に従い、**JAR 書き換え前に原本を退避するバックアップを必須の受け入れ条件に含める**(旧実装からの意図的な改善)。

## 9. カスタムファイル翻訳機能

- 選択ディレクトリ配下の `.json` `.snbt` を再帰的にスキャンする。
- 「既存翻訳をスキップ」判定は行わない(常に全件が対象)。
- **JSON**: ネストした構造をドット/ブラケット記法のキー(例 `a.b[2].c`)へフラット化し、文字列の葉ノードのみを翻訳対象とする。翻訳後、元の構造・型・順序を保ったまま値を差し戻す(数値・真偽値などの非文字列の葉は変更しない)。
- **SNBT**: ファイル全体を1つの翻訳単位として送信する。
- 出力先: 選択した最初の対象ファイルのディレクトリ配下に `translated/` フォルダを作成し、`{targetLanguage}_{ファイル名}` として書き出す(原本は変更しない)。

## 10. 進捗表示・キャンセル

- 二階層の進捗: **単一ファイル進捗**(現在処理中のジョブ内、0〜100%)と**全体進捗**(バッチ内の完了件数/総件数)。
- テキスト表示形式: 「X / Y 件完了 (Z%)」(旧 `docs/spec.md` §3.2 準拠)。
- キャンセルは**協調的**: チャンクとチャンクの間でキャンセルフラグを確認し、現在処理中のチャンクの完了を待ってから停止する。実行中の LLM への HTTP リクエスト自体は中断しない。
- **保存粒度**: キャンセル時点で完了しているチャンク(キー群)は出力ファイルに書き込み、未完了のキーは省略する。MOD のようにキー単位で複数チャンクに分割される対象では、1つの対象が「一部だけ翻訳された」状態のファイルとして残ることを許容する(クエスト・ガイドブック等はファイル全体が1チャンクのため、対象単位での保存/破棄と実質的に同じ結果になる)。未翻訳キーは元の英語のまま出力せず**省略する**(Minecraft のリソースパックは欠けたキーを MOD 本来の `en_us` にフォールバックするため、部分的な lang ファイルでも実害はない)。
- 未完了で終わった対象は、次回同じ対象を §5.5 の**差分更新**モードで再実行すれば、不足しているキーだけが自動的に埋められる。キャンセル再開の専用機構は設けず、差分更新の仕組みをそのまま流用する。
- 完了時にはシステム通知と完了サマリを表示する。

## 11. ログ機能

- 処理ログはメモリ上のリングバッファ(直近 N 件)とリアルタイム表示を持つ。
- 実行のたびにセッションディレクトリ(`logs/localizer/{sessionId}/`)へログファイルを保存する(`AGENTS.md` の「途中失敗時の復元」を追跡可能にするため必須)。
- ログには少なくとも日時・レベル(Debug/Info/Warning/Error)・処理種別・メッセージを含める(旧 `docs/spec.md` §4.1「エラーログは必ず日時を記録する」を踏襲)。
- 翻訳中は詳細ログを、アイドル時は要約ログ(進捗の節目、エラーのみ)を表示するなど、閲覧時のノイズを抑える。

## 12. バックアップ機能

- MOD 翻訳: 生成したリソースパック全体を `logs/localizer/{sessionId}/backup/resource_pack/` へコピーする。
- クエスト翻訳(FTB SNBT): 翻訳前の SNBT ファイルを `logs/localizer/{sessionId}/backup/snbt_original/` へコピーする(直接上書きするため必須)。
- Patchouli 翻訳: §8.2 の設計課題のとおり、JAR 書き換え前のバックアップを新規に追加する。
- カスタムファイル翻訳: 原本を変更しないため、追加のバックアップは不要。
- バックアップには保持期間・自動削除ポリシーを設けない(旧実装同様、明示的な削除操作のみ)。

## 13. 翻訳履歴機能

- 実行ごとに `logs/localizer/{sessionId}/translation_summary.json` を書き出す(対象言語、各項目の種別・名前・成功/失敗・翻訳キー数/全キー数)。
- 履歴ダイアログでは、セッションディレクトリを指定して過去セッション一覧(日時降順)を表示し、行を展開すると当該セッションの詳細とログを閲覧できる。
- 履歴は**現在アクティブなプロファイルディレクトリとは独立して**別ディレクトリを指定して閲覧できる。

## 14. 対象外(本移植フェーズでは扱わない)

- 自動アップデート機能(GitHub Releases からの差分ダウンロード・適用)。将来のインストーラー整備と合わせて別途検討する(`docs/specs/001-foundation.md` の対象外にも明記済み)。
- デバッグ専用の診断ツール(旧実装の `DebugLogDialog` 等)。
- macOS / Linux 向けパッケージング。Villager Translator は Windows デスクトップに限定する。
- ツール自身の UI 多言語化(英語/日本語切替)。Villager Translator は日本語 UI のみを既定とする(`AGENTS.md` 準拠)。

## 15. セキュリティ・非機能要件

- API キーはローカル設定ファイルにのみ保存し、リポジトリ・ログへ出力しない(`AGENTS.md` のドメイン制約に準拠)。
- LLM への通信はクライアント(アプリ本体)から直接行う(旧実装同様、プロキシサーバーは設けない)。
- API キーは平文の設定ファイルに保存しない。Windows の資格情報マネージャー(DPAPI)を利用したセキュアストレージ、または同等の暗号化ライブラリ(例: `flutter_secure_storage`)で暗号化して保存する。設定ファイル本体(JSON)には API キーを含めず、キー本体は OS のセキュアストレージ側、それ以外の設定値のみ設定ファイルに保存する構成とする。

**移行時の判断(API キー保存)**: API キーは LLM 呼び出し時にプロバイダーへそのまま送信する必要があるため、ハッシュ化(不可逆変換)では実装できない。**暗号化(復号可能な形での秘匿)**によって平文保存を避ける方式を採用する。旧実装は設定ファイルに平文保存していたため、この点は明確な改善点とする。
- JAR/JSON/LANG/SNBT を扱う処理は、文字コード(UTF-8 前提、BOM・制御文字の除去)、元データ保全(原本を書き換える処理は事前バックアップ必須)、部分失敗時の継続(1件のエラーで全体を止めない)を受け入れ条件に含める。
- 長時間の翻訳処理には、進捗表示・キャンセル・部分成功の扱いを必ず受け入れ条件に含める(`AGENTS.md` 準拠)。

## 16. 旧実装からの主な設計変更点(まとめ)

移植時に単純な丸写しをせず、明示的に変更する点を一覧化する。

### 16.1 意図的に維持する非対称性

- MOD はキー単位チャンク、クエスト/ガイドブックはファイル・本単位チャンクという粒度の違いは**意図的な設計**として維持する(内容の性質が異なるため)。

### 16.2 修正する不整合

| 項目 | 旧実装の問題 | Villager Translator での対応 |
|---|---|---|
| プロバイダー識別子 | 設定値 `"google"` とアダプター ID `"gemini"` が不一致 | `gemini` に統一(§4.1) |
| プロンプトプレースホルダー | `{x}` と `{{x}}` の2系統が併存し、後者は実際には置換されない | `{x}` 系に一本化(§4.3) |
| 既存翻訳スキップの重複チェック | MOD タブで最大3回同じ判定を実行 | スキャン時 + 翻訳直前の2回に整理(§4.2) |
| SNBT コンテンツ種別判定 | 判定結果が出力ロジックで未使用(死んだ配線) | 判定ロジック自体を実装しない(§7.3) |
| Patchouli 出力ファイル構造 | 複数ファイルから抽出した内容を単一フラットファイルに出力しており、公式ドキュメント・ソースコード調査の結果、Patchouli の実際のロード仕様(ディレクトリミラー方式)と一致しないと判明 | `en_us/` 相当のディレクトリ構造を `{lang}/` 配下にミラーする方式に変更する(§8.2、`docs/specs/006-patchouli-translation.md`) |
| Patchouli 翻訳前バックアップ | JAR を書き換える前のバックアップが存在しない | 書き換え前バックアップを必須の受け入れ条件に追加(§8.2, §12) |
| 既存翻訳の差分更新 | 旧 `docs/spec.md` は差分更新を意図していたが、実装は「既存なら丸ごとスキップ」の二値判定のみだった | 差分更新モードを新設し実装する(§4.2, §5.5) |
| 既存翻訳スキップの言語コード対応 | クエストのスキャン時除外判定が既定9言語のみのハードコードリストに依存し、カスタム言語を追加したユーザーには機能しなかった | 言語コードに依存しない汎用的な存在チェック(§5.5 の差分更新と共通のキー比較ロジック)に統一する |
| API キーの保存方式 | 設定ファイルに平文で保存していた | 暗号化(復号可能)によるセキュアストレージに保存する(§15) |
| FTB Quests(KubeJS)の出力先 | 旧 `docs/spec.md` の設計意図(2箇所出力)に対し、実コードは `kubejs/assets/kubejs/lang/` のみに出力していた | 旧実装を不備と判断し、`kubejs/assets/kubejs/lang/` と `kubejs/assets/ftbquests/lang/` の両方へ出力する(§7.1)。実機での動作確認は §16.4 参照 |

実際の Minecraft/MOD 側仕様との整合性が未確認で、誤った出力構造を実装すると手戻りが大きい項目。該当する `docs/specs/00N-*.md` の着手前に検証を完了させ、対象外として先送りしない。

| 項目 | 内容 | 参照 |

旧アプリの設計意図(`docs/spec.md`)と実際の挙動が食い違っていた項目のうち、対応方針は決定済みで実装をブロックしないが、念のため該当機能の実装後に実機での動作確認を行い、必要であれば仕様を更新するもの。

## 17. 実装順序案

`AGENTS.md` の「各機能を仕様書、テスト、実装の順に小さく移行する」方針に従い、以下の順で `docs/specs/00N-*.md` を切り出すことを提案する。依存関係を踏まえた順序であり、各回で該当セクションの受け入れ条件を具体化する。

1. `002-settings-and-llm-adapter.md`: 設定画面の基盤(§4)+ LLM アダプター境界(§5.1)。実際の翻訳呼び出しは含めず、モックアダプターでの疎通確認まで。
2. `003-translation-engine.md`: チャンク分割・応答検証・リトライ(§5.2〜5.3)。単体テストで担保できる範囲。
3. `004-mod-translation.md`: MOD スキャン・翻訳(§6)。最も単純な出力形態(新規リソースパック)から着手する。
4. `005-quest-translation.md`: FTB Quests / Better Quests(§7)。SNBT 直接上書きのリスクが高いため、バックアップの受け入れ条件を必須にする。
5. `006-patchouli-translation.md`: Patchouli ガイドブック(§8)。出力仕様(ディレクトリミラー方式)は公式ドキュメント調査により決定済み。実装後に実機確認するタスク(§16.4)を含める。
6. `007-custom-files-translation.md`: カスタムファイル翻訳(§9)。
7. `008-progress-log-history.md`: 進捗・キャンセル・ログ・バックアップ・履歴の横断機能(§10〜13)を、上記機能追加と並行しつつ最終的に整理する回として設ける。

## 18. 将来検討事項(Could)

今回の移植サイクルの対象外とするが、翻訳ツールとしての価値向上のため将来検討したい項目。MoSCoW 分類で **Could**(今回のサイクルでは実装しない)とする。

- **翻訳実行前の概算コスト表示**: 選択した対象の総キー数・概算トークン数から、想定 API 呼び出し回数や概算コストを翻訳開始前にプレビュー表示する。大量の MOD/クエストを一括翻訳する際、API 課金が発生することをユーザーが把握しないまま実行してしまうリスクを軽減する。
